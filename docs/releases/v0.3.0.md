# FairShare v0.3.0 — Secure Multi-Household Isolation

**Release status: prepared; production data migration and operational verification are required before release.**

## Summary

FairShare now supports multiple unrelated households with household-scoped APIs, active-membership authorization, and a global active-household selector. The selected household in the client is only a navigation choice; the server independently verifies membership on every protected request.

## Included

- Require `householdId` for chores, expenses, events, and chat messages.
- Scope resource reads, updates, and deletes to the authorized household.
- Validate chore assignees, expense participants, event attendees, and chat related records against household membership.
- Authorize household resource endpoints and Socket.IO with active `HouseholdMembership` records.
- Add owner/member management and expiring, rotatable, revocable invite codes.
- Remove the unscoped chore, expense, event, and chat route mounts, along with the shared default-household fallback.
- Add a global active-household selector with household creation/joining and scoped UI requests.
- Add a rerunnable dry-run migration for legacy `householdId` and membership data.
- Run the server test suite in CI.

## Isolation test coverage

HTTP route tests use an in-memory data store and exercise actual Express routers. They verify member success and cross-household denial for:

| Surface | Isolation checks |
| --- | --- |
| Chores | List, get, create, update, delete, cross-household IDs, assigned member validation, protected ownership |
| Expenses | List, get, create, update, delete, balances, cross-household IDs, payer/split validation |
| Events | List, ranges, upcoming, unpaid bills, get, create, update, pay, delete, attendee validation |
| Messages | History, post, legacy `roomId` reads, related-item validation |
| Socket.IO | Authorized join/send, guessed household IDs, denial consistency, household-only broadcast |
| Household/member APIs | Membership-required reads, owner-only actions, member removal/leave, shared-household roommate listing |

These are API/router tests, not tests against a production MongoDB deployment. Operational validation should include a reviewed migration dry run and a post-migration check.

## Required rollout checklist

1. Back up MongoDB and verify that the backup can be restored.
2. Deploy code that supports legacy data and the migration command.
3. Run and review the dry run in [MIGRATION.md](../MIGRATION.md), supplying the explicit destination household ID for records without an owner.
4. Apply the migration and verify that a second dry run reports no pending changes or failures.
5. Verify existing users can access their household-scoped data and that unrelated test users cannot.
6. Only then mark the production rollout complete and tag `v0.3.0`.

The script does not infer a household for unowned records. Legacy chat `roomId` values are preserved when they match an existing household; unmatched values are reported for manual review.

## Compatibility notes

- The MongoDB `rooms` collection remains the backing collection for `Household`.
- Chat message `roomId` compatibility remains temporarily.
- Global profile operations (`GET /roommates/me`, `PUT /roommates/me`) remain global by design; household member listing/removal is separate.
- The previous unscoped `/chores`, `/expenses`, `/events`, and `/chat` resource routes are no longer mounted.
